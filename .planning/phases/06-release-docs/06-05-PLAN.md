<objective>
Put the shipped documentation in front of a person who is starting from nothing and find out whether
it is actually sufficient — after the developer decides, explicitly, whether that person downloads
from a real published Release or from a build artifact.

Purpose: this is the phase goal, not a check on it. Everything the previous four plans wrote is a
hypothesis about what a user needs; D-15 is the experiment. The sequencing decision underneath it is
genuinely open (RESEARCH Open Question 1, CONTEXT Deferred Ideas) and genuinely one-way: a real
`v*` tag push is the only thing that can prove `body_path` renders as intended and the only thing
that closes Phase 5's outstanding UAT item, and it is also a public release that cannot be recalled
from anyone who has already downloaded it.

Output: an end-to-end verification record, the captured first-launch dialog wording, and a
documentation-gap list that is fixed rather than filed.
</objective>

  <name>Task 1: Decision — verify against a real `v*` tag Release, or against a `workflow_dispatch` artifact</name>
  <decision>Does the end-to-end verification download from a real `v*` tag Release, or from a `workflow_dispatch` build artifact?</decision>
  <context>
This is the one sequencing question CONTEXT.md and RESEARCH.md both left open for planning, and it
is a one-way door: once a `v*` tag is pushed, the workflow publishes a GitHub Release that is
visible to every visitor of the repository. Deleting the tag and the Release afterwards does not
recall anything already downloaded.

What hangs on it:

- **`body_path` rendering is unverifiable without it.** The `release` job is guarded by
  `if: startsWith(github.ref, 'refs/tags/')`, so on a branch dispatch it is always skipped. Plan
  06-01's dispatch regression proved the YAML parses and the job graph is intact; it could not and
  did not prove what the Release body actually looks like. That gap is D-09's documented residual
  risk.
- **Phase 5's outstanding UAT item needs exactly this action.** `.planning/phases/05-ci/05-UAT.md`
  test 1 is pending on a real tag push, and its own note advises doing it when actually releasing
  rather than pushing a tag purely to test.
- **Authenticity of the verification.** D-15's premise is a person acting only on shipped
  documentation. Downloading from a real Release page is the experience a real user has; downloading
  a CI artifact requires being signed in to GitHub, navigating a workflow run, and unzipping — none
  of which the documentation describes, so those steps would have to be excluded from the
  verification and the result would be correspondingly weaker.
- **A version bump comes with option A.** The repository is at `0.1.16` in
  `frontend/package.json` and in both `version=` fields of `backend/main.py`. The `Resolve version`
  step runs `scripts/release/check_version_consistency.py`, which requires the tag, with one leading
  `v` removed, to equal both of those. Publishing this milestone as `v0.2.0` therefore means bumping
  all three first; the workflow will fail the run otherwise.
  </context>
  <options>
    <option id="option-a">
      <name>Push a real `v0.2.0` tag and verify against the published Release</name>
      <pros>The only way to observe how `body_path` actually renders in a Release body; simultaneously closes Phase 5's pending UAT item; gives the verifier the authentic download experience a real user has; ships the milestone this roadmap exists to ship.</pros>
      <cons>Irreversible in the sense that matters — the Release is public the moment it is created, and any download cannot be recalled. Requires bumping the version in three places first. If the release body renders badly, the fix ships as a follow-up release rather than a quiet correction.</cons>
    </option>
    <option id="option-b">
      <name>Trigger `workflow_dispatch` and verify against the downloaded build artifact</name>
      <pros>Nothing becomes publicly visible; fully reversible; the dmg under test is byte-identical to what a tag build would produce, so every part of the walkthrough after the download is equally valid.</pros>
      <cons>`body_path` rendering stays unverified and must be recorded as an open residual risk carried past this phase; Phase 5's UAT item stays pending; the verifier acquires the dmg by a route the documentation does not describe, so the download step itself is excluded from the D-15 experiment.</cons>
    </option>
  </options>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 3: Clean-account end-to-end run using only the shipped documentation (D-13 / D-15)</name>
  <what-built>
The complete Phase 6 documentation set is now live across four surfaces, and a dmg produced by the
real build pipeline is ready to install:

- The GitHub Release body (or, under option B, `.github/RELEASE_NOTES_TEMPLATE.md` as it would
  render) carrying the bilingual prerequisite checklist, the GUI self-check, the progressive 放行
  walkthrough, and the trust caveat
- `README.md` and `README_EN.md` download sections carrying the two-line prerequisite pointer
- The regenerated dmg drag-install background describing the measured first-run flow
- The in-app first-launch notice, rewritten in both locales, reachable again later from
  Settings → 平台限制说明

Automated checks already passing: the full Python suite, the full Node suite, the three-way
verbatim lock on the terminal command, the forbidden-fragment sweep across every text surface, and
the pixel-dimension and retina-TIFF checks on the regenerated images.

What no automated check can establish, and what this checkpoint is for: whether the documentation
is *sufficient* — whether a person who knows nothing about this project can get from a download
link to a running Chrome profile using only what is written down.
  </what-built>
  <how-to-verify>
**Setup (do this from your own account, before switching):**

1. Delete any existing `Open-Anti-Browser.app` from `/Applications`. That directory is shared
   across accounts, so a leftover install would make the new account's experience untruthful.
2. Create a new standard macOS user account (系统设置 → 用户与群组). D-13 requires this because the
   `LSQuarantineEventsV2` database and Gatekeeper decision records are per-user, and your own
   account is already contaminated by Phase 5's testing — it carries a Gatekeeper denial record and
   several quarantine rows for this app.
3. Put the acquired dmg somewhere the new account can read, and note the path.
4. Arm a log capture before the first launch, as 05-06 did: stream `syspolicyd`, `amfid`, and
   kernel messages to a file. Phase 5's single most valuable finding came from having this running
   before the first double-click, and its absence would leave you relying on recollection — which
   05-06 proved is unreliable for exactly this sequence.

**The verification run (log in as the new user):**

5. Open only the Release page (option A) or the rendered template (option B), plus the README if
   the Release page points you there. Read them as a new user would.
6. Perform the hardware and OS self-check exactly as written, using the Apple menu path. Confirm it
   is followable without a terminal.
7. Install the app from the dmg by dragging it to Applications, following whatever the dmg window
   itself says.
8. Double-click the app. Expect it to be blocked and to close itself. **Before doing anything
   else, photograph or screenshot the dialog and write down its title and both button labels
   verbatim.** This is the wording gap Phase 5 accepted and deferred to this phase; it will not be
   recoverable later.
9. Follow the documented walkthrough from step 1 onward and see whether the app opens.
10. Once the app is open, create a Chrome profile and start it. Confirm a fingerprint Chromium
    window actually appears.
11. Stop the profile and quit the app with Cmd+Q. Confirm nothing is left running.

**The scoring rule — this is the actual test (D-15):**

At every step, ask: *did I just use something the documentation did not tell me?* Navigating to
System Settings from memory, typing a command you remembered, knowing to try again because you
wrote the docs — each of those is a **documentation gap**, not a pass. Write each one down as it
happens, with what you did and what the documentation should have said instead. You are both the
verifier and the author here, which makes this the largest blind spot in the phase; the only
defence is recording the moment rather than rationalising past it.

**Also record:**

- Whether the second double-click was sufficient, or whether you needed the System Settings
  fallback, or the terminal command. All three outcomes are informative — the primary path has only
  ever been observed on one machine.
- The output of checking the app bundle's quarantine attribute after the first launch, and the
  Gatekeeper assessment result, so "it runs but is not approved" is measured on this account too.
- Whether the process path contains an App Translocation component.

**Then close the loop:** every documentation gap you recorded gets fixed in
`.github/RELEASE_NOTES_TEMPLATE.md` (and mirrored to the other surfaces if it touches shared copy),
and the parity checks from plan 06-04 are re-run afterwards. A gap that is only filed is a gap that
ships.
  </how-to-verify>
