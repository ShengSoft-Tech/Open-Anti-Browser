English section, placed above the 放行 walkthrough (a reader decides whether to download before

(1) **Prerequisite checklist (D-05).** Two required conditions, stated as a checklist and not as a
choice: an Apple Silicon (M-series) chip, and macOS 15 or newer. Cite `macOS 15` exactly — the
placeholder `12.0` and the sampled `13.0` from earlier Phase 5 plans are both superseded, and
`build-release.yml` ships `LSMinimumSystemVersion` at `15.0`. State plainly that only one package
is published for this version and that it is arm64; do not present a download choice, do not
describe an Intel build as planned, upcoming, or available elsewhere.

(2) **Self-check method (D-06), GUI first.** The primary instruction is the Apple menu path: the
Apple logo in the top-left corner → 关于本机 / About This Mac → read the 芯片 / Chip row (it must
name an Apple M-series chip) and the macOS version number (it must be 15 or higher). Append the
two-command terminal alternative `uname -m && sw_vers -productVersion` afterwards, explicitly
framed as optional and for readers who already use a terminal, together with what a passing result
looks like (`arm64` and a version number of 15 or higher). The GUI path leads because the target
reader is assumed not to use a command line — that is the entire premise of this phase.

(3) **Expected outcome on unsupported hardware (D-07, D-08).** Two short sentences: a Mac running
macOS earlier than 15 will be refused by the system when opening the app, and an Intel Mac cannot
run this arm64-only package. Word both conservatively — describe the outcome, do not quote or
invent a system dialog's wording. Add one sentence recording that neither outcome has been
observed on real hardware and that both are inferred from the app's declared minimum system version
and its single-architecture build. Do not add any runtime check to the application for this: D-07
scopes runtime detection out, and a build declaring `LSMinimumSystemVersion` 15.0 is refused by the
OS before any application code executes, so such a check could never run on the failing case.

(4) **Trust caveat (RESEARCH Pitfall 4, 05-06 Open Item 4).** One short paragraph in each language,
stated plainly and without apology: this application is not signed with an Apple Developer ID and
is not notarized; after the 放行 steps it runs because the one-time quarantine mark is gone, not
because macOS approved it; a Gatekeeper assessment of the bundle still reports a rejection. Frame
this as normal for an ad-hoc-signed application. Any phrasing that describes the application as
having been approved, or that describes Gatekeeper as trusting it, or that otherwise implies Apple
vouches for the build, is forbidden — it is factually wrong and would mislead a reader into
believing a trust relationship that does not exist. The exact phrase patterns the gate rejects are
enumerated in the acceptance criteria below.

Keep the existing bilingual layout: the Chinese section stays first and complete, the English
section second and complete, each self-contained so a reader of either language never has to read
the other. Do not restructure or re-word plan 06-01's walkthrough, and do not alter the fenced
command block — the consistency lock asserts it byte-for-byte.
