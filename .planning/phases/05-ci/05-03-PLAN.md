  <action>
    在 `.github/workflows/build-release.yml` 的 `jobs:` 下、既有 `build` job **之后**新增一个平级 job `build-macos`,`runs-on: macos-15`(ROADMAP SC1 的 arm64 runner;**不加 `matrix:`、不加第二个架构** —— x64 已于 2026-07-27 移出 v0.2)。工作流顶部的 `name:`、`on:`、`permissions:` 三段以及既有 `build` job 的每一行**逐字不动**。

    `build-macos` 的步骤按下列顺序与名称落地(名称要稳定,05-04 会按名称插入与替换步骤):

    **`Checkout` / `Set up Python 3.11` / `Set up Node.js 20` / `Install Python dependencies` / `Build frontend`** —— 与 windows job `:17-37` 逐字同构(两平台共用同一份 `requirements.txt`,不拆分)。`Build frontend` 必须排在 pyinstaller 之前:`frontend/dist` 是 `--add-data` 的输入,而 `npm run build` 的 prebuild/postbuild 钩子会跑 `python -m backend._g` 校验源文件哈希,所以也必须排在 Python 依赖安装之后。

    **`Install create-dmg`** —— `brew install create-dmg`(D-09;RESEARCH 已核实为 Homebrew core 官方 bottle,不得改用第三方 tap 或直接下载脚本执行)。

    **`Resolve version`** —— 计算 `APP_VERSION` 并写入 `$GITHUB_ENV` 供后续步骤复用:`github.ref` 以 `refs/tags/` 开头时取 `github.ref_name` 去掉前导 `v`(与 windows Inno Setup `:98` 同构);否则(即 `workflow_dispatch` 手动触发,此时 ref 是分支名)读 `frontend/package.json` 的 `version` 字段作为取值,保证 D-04 要求的「手动触发时两个 build job 正常跑并传 artifact」不会因为拿不到 tag 而失败。用 `python3 -c` 读 json,不引入 `jq`。**05-04 会把这一步升级成带三方一致性校验的版本**,本任务先只做取值。

    **`Prepare browser engine (macOS arm64)`** —— 照 RESEARCH「Code Examples / macOS 内核下载与注入」实现,并注意三点:内核 URL 用 `python3 -c` 从 `backend.config` 读 `CHROME_ENGINE_ZIP_URL_MACOS_ARM64`(沿用 `:62` 的单一事实源约定,内核版本不在 yml 里硬编码);解压用 `ditto -x -k` 而非 `unzip`(保符号链接与既有签名);解压目标是 `$RUNNER_TEMP` 而非仓库树内(沿用 `:48` 那条既有注释的理由)。把**原始的、未经任何拷贝的**内核保留在 `$RUNNER_TEMP/kernel/Chromium.app` 供后面注入使用,同时在仓库树内建一个只含占位文件的 `engines/chrome/` 目录 —— 后者的唯一作用是让 pyinstaller 的 `--add-data "engines:engines"` 建出目录结构与符号链接,不让 pyinstaller 去搬 400MB 的内核(它不保证保留符号链接与签名)。步骤开头先 `rm -rf` 目标目录再建,保证重跑幂等。

    **`Build app with PyInstaller (onedir, .app bundle)`** —— 照 RESEARCH「Code Examples / macOS pyinstaller 调用」逐字采用。按 D-05,构建声明**全部内联在 CLI 参数里,不引入 `.spec` 文件** —— 这是为了不动 `.gitignore` 里忽略 `*.spec` 的既有约定,也保持两平台命令行风格一致;CLI 覆盖不到的键留给下一步的 `plutil` 补。相对 windows `:73-89` 的四处必改(Pitfall 6):`--add-data` 分隔符全部由分号改成冒号;`--icon` 换成 `assets/app.icns`;去掉 `ruyipage` 那条 hidden-import(该包在 macOS 未安装,见 `requirements.txt` 的 `sys_platform` 标记);新增 `--osx-bundle-identifier "com.shengsoft.openantibrowser"`(取值对齐仓库所属的 GitHub 组织 `ShengSoft-Tech`)。`websockets` 三条 hidden-import 与 `--collect-submodules "curl_cffi"` 保留(跨平台依赖)。

    **`Patch Info.plist`** —— 照 RESEARCH Pattern 3 用 `plutil -replace` 补三个键到 `dist/Open-Anti-Browser.app/Contents/Info.plist`:`CFBundleShortVersionString` 与 `CFBundleVersion` 取 `$APP_VERSION`,`LSMinimumSystemVersion` 取字符串 `12.0`(RESEARCH Assumptions Log **A3 标记为未验证**,05-04 会加一道 `otool -l` 断言把它核销)。**不要**手工补 `NSHighResolutionCapable` / `CFBundleName` / `CFBundleDisplayName` / `CFBundleIdentifier` / `CFBundleIconFile` —— RESEARCH 已实测确认这些由 pyinstaller CLI 自动写入。补完立刻 `plutil -p` 打印整份 plist 到日志备查。**这一步必须排在后面所有 codesign 调用之前**(Pitfall 1)。

    **`Inject Chrome kernel into .app`** —— 先断言 `dist/Open-Anti-Browser.app/Contents/Frameworks/engines` 存在且是符号链接(这是 `config.ENGINES_DIR` 在冻结态解析正确的前提,RESEARCH Pattern 1 的实测结论);若断言不成立,显式建出该符号链接并在日志里打一条醒目的偏离告示(SUMMARY 要记录是否触发)。随后 `rm -rf` 掉 pyinstaller 拷进去的占位内容,用 `ditto` 把 `$RUNNER_TEMP/kernel/Chromium.app` 注入到 `Contents/Resources/engines/chrome/Chromium.app`。用 `ditto` 而非 `cp -R` 是因为只有它保留符号链接与既有签名封套。注入后 `ls -la` 打印内核目录结构。

    **`Enumerate nested bundles and minimum OS versions (A2/A3 diagnostics)`** —— 纯诊断步骤,不做断言,但输出会成为核销两条 RESEARCH 假设的一手证据。用 `find "dist/Open-Anti-Browser.app" \( -name "*.app" -o -name "*.framework" \) -print | sort` 枚举全部嵌套 bundle(`find` 默认不跟随符号链接,所以不会经 `Contents/Frameworks/engines` 重复走进内核子树);再对 `Contents/Frameworks` 下几个 Qt 相关二进制跑 `otool -l` 并 grep 出 `LC_BUILD_VERSION` 的 `minos` 值。前者核销假设 **A2**(PySide6/QtWebEngine 的嵌套结构此前只是按 Chromium 结构类比推断),后者为 **A3**(`LSMinimumSystemVersion` 取值)提供实测依据。

    **`Sign nested bundles and app (layered ad-hoc)`** —— 照 RESEARCH Pattern 2 的实测序列由内向外逐层 `codesign --force --sign -`:先 `Chromium Framework.framework/Versions/Current/Helpers` 下的每个 `.app`,再 `Chromium Framework.framework/Versions/Current`,再内嵌的 `Chromium.app` 本身;接着处理 Qt/PySide6 侧 —— 用上一步同样的 `find` 枚举 `Contents/Frameworks` 下的嵌套 bundle(排除内核子树,它已单独处理完),**按路径深度倒序**(最深的先签)逐个签名,其中 `*.framework` 目标若存在 `Versions/Current` 则签该子路径、否则签 framework 本身;最后签最外层 `dist/Open-Anti-Browser.app`。**外层与内层的签名调用都不得携带递归签名开关**(D-13;Pitfall 2 已实测该开关对嵌套 bundle 是空操作)。任一 `codesign` 失败即整步失败,不吞 stderr。

    **`Verify code signatures (outer + nested kernel)`** —— 这是 PKG-03 的硬门禁,两条断言缺一不可:对 `dist/Open-Anti-Browser.app` 跑一次 `codesign --verify --deep --strict`,再对 `dist/Open-Anti-Browser.app/Contents/Resources/engines/chrome/Chromium.app` **单独**跑一次同样的命令。任一失败即中止(Pitfall 2:只验外层会给出假阳性通过)。注意 Pitfall 3:内核资产在**重签之前**本来就过不了这条验证,所以本步骤必须排在签名步骤之后 —— 不要在下载/注入之后立刻加一道「先验一下内核」的门禁,那会必然失败。

    **`Create dmg`** —— 先做幂等清理:`rm -f` 目标 dmg,`hdiutil detach` 掉可能残留的同名卷(失败忽略)。用 `tiffutil -cathidpicheck assets/dmg-background.png "assets/dmg-background@2x.png" -out "$RUNNER_TEMP/dmg-background.tiff"` 把 05-01 的两张图合成多分辨率 tiff(这是 macOS 让 dmg 背景图支持 retina 的标准做法)。把 `.app` 用 `ditto` 复制到一个干净的 `$RUNNER_TEMP/dmg-src/` 目录里作为 create-dmg 的源目录(避免 create-dmg 直接吃 `.app` 时的行为歧义,同时 `ditto` 保签名)。然后调 `create-dmg`,参数:卷标 `Open-Anti-Browser $APP_VERSION`、背景用上面那份 tiff、窗口位置 200 120、窗口尺寸 600 400、图标尺寸 128、应用图标落点 150 190、`--app-drop-link` 落点 450 190、隐藏扩展名、不启用互联网。输出文件名 **`Open-Anti-Browser-${APP_VERSION}-arm64.dmg`**(D-11 的架构后缀必须保留)。**不要**给 create-dmg 调用加吞掉退出码的兜底 —— RESEARCH 假设 A4 指出它在 CI 会话类型下的 AppleScript 行为未经真实验证,第一次跑要让真实退出码与完整日志暴露出来。

    **`Verify dmg contents`** —— 挂载刚产出的 dmg 到 `$RUNNER_TEMP` 下的临时挂载点(`hdiutil attach -nobrowse -readonly -mountpoint`),断言四件事:`Open-Anti-Browser.app` 存在;指向 `/Applications` 的别名存在;`.background` 目录存在(证明背景图真的进了 dmg);对挂载点里的 `.app` 与其内嵌 `Chromium.app` 再各跑一次 `codesign --verify --deep --strict`(证明签名在 dmg 打包后依然完好)。断言完 `hdiutil detach`。

    **`Upload macOS dmg artifact`** —— `actions/upload-artifact@v4`,`name: Open-Anti-Browser-macos-dmg`,`path: Open-Anti-Browser-*-arm64.dmg`,`if-no-files-found: error`(与 windows `:105-110` 同构)。本 job **只上传 artifact,不建 Release** —— 汇合发布由 05-05 新增的 `release` job 统一处理(D-02)。

    全部 bash 步骤统一用 `shell: bash` 并在脚本开头 `set -euo pipefail`,沿用 `verify_and_upload_macos_kernel.sh` 的「失败立即打印可定位的错误信息并以非零退出码中止」风格。
