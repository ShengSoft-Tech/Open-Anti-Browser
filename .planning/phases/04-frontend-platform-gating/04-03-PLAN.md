<objective>
把 04-01 证明过的门控链路铺到配置列表:macOS 上的引擎筛选下拉不再提供 Firefox,而从 Windows 迁移来的既有 Firefox 配置继续可见、带明确的「仅 Windows」标记、启动被禁用(单行与批量两条路径一致),删除入口完好无损。

Purpose: UI-01 的验收面不止创建对话框。列表是用户看见既有 Firefox 配置的唯一地方,D-01 明确要求「不删不藏、禁用启动、保留可删除」。同时 RESEARCH Pitfall 4 指出行内启动按钮与批量启动是两条独立的代码路径,只禁前者会让「启动全部」照样对 Firefox 配置发起注定失败的请求、把清晰的平台提示退化成一条原始后端报错。

Output: `ProfileList.vue` 上的四个门控消费点(筛选下拉、行内标记、启动禁用、批量启动过滤)。
</objective>

  <action>
    新增一个本地判定函数 `isProfileStartBlocked(row)`:当 `row.engine === 'firefox'` 且 `firefoxEngineVisible` 为假时返回 true,其余返回 false。这是本文件里「这个配置在当前平台能不能启动」的唯一判定,三个调用点都必须走它,不得各写各的条件表达式。

    调用点一(行内启动按钮):把 `isProfileStartBlocked(row)` 或进现有的 `:disabled` 表达式(现有条件是 starting 状态与 `store.isProfileStarting(row.id)`,保留不动),并把该按钮包进一个 `el-tooltip`,`:disabled` 绑 `!isProfileStartBlocked(row)`(即只有被平台门控挡住时才显示气泡),`content` 取 `t('platformLimits.startBlockedHint')`,`placement` 设 `top`。注意 Element Plus 的 disabled 按钮不派发鼠标事件,tooltip 要包在按钮外层才能触发。

    调用点二(`handleStart`):在函数开头的早退判断里追加 —— 命中 `isProfileStartBlocked(row)` 时直接 return,不发请求。这是防御性兜底,防止将来有别的路径调到它。

    调用点三(`handleBatchStart`):在 `queuedIds` 的过滤链里追加一个 `.filter(item => !isProfileStartBlocked(item))`,位置放在既有的 status/starting 过滤之后。这样「启动选中项」会跳过被门控的 Firefox 配置,而不是逐个发起注定失败的请求、把清晰的平台提示退化成一串原始后端报错。成功提示里的数量 `queuedIds.length` 自然反映实际启动数,不需要额外改动。

    可复制性(D-01 留给 planner 的裁量):把「更多」下拉里的复制项在 `isProfileStartBlocked(row)` 为真时禁用(`el-dropdown-item` 的 `disabled` 属性),理由是复制一个 Firefox 配置等于在 macOS 上新建了一个 Firefox 配置,与 SC1「创建配置不出现 Firefox」相冲突。**删除项必须保持始终可用**,任何平台、任何引擎都不加禁用条件 —— D-01 要求数据「保留可见与可删除,不静默丢数据」。编辑按钮也保持可用:用户仍需要改代理、备注等设置,引擎字段本身已由 04-01 在对话框里锁定。

    停止按钮不加任何门控:一个已经在运行的进程必须永远能被停下来。
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 前端启动门控 → 后端 `/api/profiles/{id}/start` | 前端禁用只是 UX;后端在 macOS 上独立拒绝 Firefox 启动(Phase 1/3 已实现并测试) |
| 用户 profiles.json 数据 → 列表呈现与操作入口 | 门控条件如果作用到列表可见性或删除入口,会让用户认为数据已丢失 |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-08 | Denial of Service(用户对自己数据的可及性) | ProfileList 行可见性与删除入口 | high | mitigate | 门控只作用于筛选下拉选项、行内标记、启动/复制三处;列表数据源 `store.filteredProfiles`、行渲染、删除入口一律不加平台条件。验收项以 `sed` 断言删除入口无 `disabled`、以 diff 断言数据源未被条件化。 |
| T-04-01 | Elevation of Privilege | 前端启动门控 | low | accept | 门控是 UX affordance,不是访问控制边界;后端独立拒绝非 Windows 上的 Firefox 启动。 |
| T-04-09 | Information Disclosure | 批量启动的错误回显 | low | mitigate | 批量启动预先过滤掉被门控项,避免把原始后端错误串直接抛给用户;用户看到的是本地化的平台说明。 |
| T-04-SC | Tampering | 依赖供应链 | low | accept | 本 plan 不执行任何 npm/pip/cargo 安装,无新增第三方包,包合法性门禁不适用。 |
